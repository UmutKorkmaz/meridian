# Meridian.Mediator.Redis

Owned Redis leases for Meridian idempotency, targeting .NET 8, 9 and 10. The optional core `ILeasedIdempotencyStore` contract is selected before the legacy atomic/base paths. Those paths keep their prior behavior for stores without the optional interface.

Register an application-lifetime `IConnectionMultiplexer`, an explicit `CacheContractRegistry` (stable ID, schema and `JsonTypeInfo`), then call `AddMeridianRedisIdempotency(registry, options => ...)`. Registration is scoped, preserves custom `IIdempotencyStore` and scoped serializers, and aliases the concrete, leased and base interfaces to the same scoped instance. Repeated registration uses the first option snapshot. Register an authenticated scoped `ICacheKeyScope` when responses are private. The optional package depends on Caching and core; neither core depends on Redis.

`LeaseDuration` defaults to 30 seconds; `CompletedRetention` defaults to 24 hours. Durations must be positive whole milliseconds at most `Int32.MaxValue` milliseconds. `MaximumEntryBytes` defaults to 1 MiB, including the Caching envelope. All options are copied at construction. The registry freezes before use. A scoped identity must remain immutable throughout the request; changing and reverting identity between observations cannot be detected universally.

A claim uses the declared response type, allowing completed null replay. Each key is one strict versioned hash. Lua uses Redis TIME and compares the owner, state, declared contract/schema and lease deadline atomically. Renewal extends by the original stored duration even through another adapter with different defaults. Pending hashes have **no automatic TTL**. An expired pending record returns `OutcomeUnknown`; it is never reacquired or evicted automatically. Corruption, unknown contracts/schema, malformed payloads and contract mismatch fail closed and retain the key. Ordinary-cache deletion/miss policies do not apply.

`IdempotencyLease.Key` is already the effective key and is used verbatim for renew/complete/release. Logical claim/check/store/reconciliation inputs apply application prefix and authenticated scope exactly once. Decorated tuples are injective; arbitrary raw passthrough can equal a decorated key. Require trusted uniformly decorated clients with no untrusted raw access, or an isolated physical namespace. Prefixes are not access control. Namespace/schema migrations must preserve retained pending protection and explicitly reconcile records; a cold-cache cutover is unsafe here.

The core directly awaits the handler exactly once and runs one sequential renewal loop within that request. Its fixed cadence is one third of the conservative local acquisition expiry snapshot, with at least 1 ms usable cadence. The adapter projects server remaining time minus the full monotonic round trip onto local receive UTC; this is an acquisition/scheduling snapshot, not renewed authority. Renewals reuse the same immutable lease. Scheduler stalls or clock jumps can impair liveness; Redis time decides transitions. The request delegate has no private lease-loss cancellation parameter, so loss of ownership does not stop an already running business handler.

After handler termination the loop is stopped and joined; no scoped provider work is abandoned. Provider cancellation is cooperative, including the five-second cleanup budget: a custom provider that ignores cancellation can keep the request pending until its operation settles. Redis waits materialize all bytes before command issuance and can end on cancellation while a static observer observes eventual transport faults. Already issued Redis commands can still apply. The borrowed multiplexer must outlive those outstanding commands (normally application lifetime); the adapter never disposes it. There is no automatic retry of ambiguous transport failures.

A handler exception or cancellation never proves that business effects were absent. Core retains the claim, stops renewal, preserves the original exception and suppresses Meridian retries. Pending may still report InFlight until its deadline, then OutcomeUnknown. Renewal false, timeout, provider error or invalid claim cannot authorize another execution. A single real error keeps its exact exception identity/stack; multiple real errors aggregate exact references in handler-first order. Expected stop cancellation does not invent a second error. Post-handler provider exceptions are uncertain regardless of their exception type. External/manual retry systems must honor this uncertainty too.

After a successful handler the core attempts completion once with a fresh independent five-second token, even if the caller canceled after producing the result. Failure does not release or rerun work. Successful completion returns the response, including null. An identical owner/payload repeated completion is a no-op without extending retention. Completion can race expiry and require reconciliation.

`ReconcileAsync(logicalKey, expectedOwnerToken, Completed | SafeToRetry, response, ct)` requires an expired valid pending record, matching owner, locally known recorded contract/schema and an atomically revalidated snapshot. **The application must first establish that the old handler and outstanding commands are quiescent.** Expiry or an owner token cannot fence a business effect still running elsewhere. Completed records an externally established result using the retained contract, including null. SafeToRetry requires null response and explicit evidence that a retry is safe; it deletes protection. Missing/changed/live/corrupt records reject. No business rollback is inferred.

Legacy Check returns absent or a completed result; pending throws in-progress/unknown. Legacy Store accepts only a non-null allowlisted value at an absent key and refuses both pending and completed overwrite. Completion retention expiry, administrative deletion, eviction, namespace changes, lost persistence or failover data loss end replay protection. Configure Redis eviction/persistence/replication accordingly. This is not an exactly-once guarantee for external effects and not a guarantee against Redis failover loss.

The required provider suite uses independent connections and actual application subprocess kills before/after effects and after completion. A separate uniquely owned Redis container is hard-restarted against its own AOF data with `appendfsync always`, with fresh clients and changed server run_id. That proof is limited to one standalone restart/filesystem configuration, not disk/power loss, replica promotion, multi-region failover or other persistence policies. Missing selected Redis or Docker fails the support gate rather than skipping. Tests only remove their exact owned keys/containers/processes; they never FLUSHDB.
